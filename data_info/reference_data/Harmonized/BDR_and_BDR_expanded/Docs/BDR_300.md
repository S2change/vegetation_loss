# BDR – Detailed Processing Workflow README

This document provides a detailed, step-by-step description of the full processing workflow applied to the **BDR_CCDC_TNE_v3** dataset. It explicitly identifies the scripts used at each stage, the expected inputs and outputs, and the location of each component within the current `BDR_DGT_300` repository structure.

This README documents the standard **BDR** workflow only. The **BDR expanded** layer is processed through a separate runner and is not included in the BDR execution sequence described below.

---

## 2. Processing order and execution sequence

The BDR workflow must be executed in the following order:

```text
1. Text normalization
   run_normalize_string.py
            ↓
2. Preliminary overlap analysis
   run_topology.py
            ↓
3. Harmonization and final export
   run_process_layer_BDR.py
```

The commands should be executed from the `BDR_DGT_300` directory:

```bash
python Codes/runners/run_normalize_string.py
python Codes/runners/run_topology.py
python Codes/runners/run_process_layer_BDR.py
```

Each stage produces the input required by the following stage.

### 2.1 Stage 1 — Text normalization

**Runner:**

```text
Codes/runners/run_normalize_string.py
```

**Utility:**

```text
Codes/utils/normalize_string.py
```

**Input:**

```text
Data/BDR_CCDC_TNE_v3.shp
```

**Output:**

```text
Results/Normalized_text_columns/BDR_CCDC_TNE_v3_textnorm.shp
```

This stage normalizes the values stored in text fields by:

- converting text to lowercase;
- removing accents and diacritics;
- removing leading and trailing spaces;
- preserving NULL values.

This stage normalizes attribute **values**, not the final harmonized field names.

### 2.2 Stage 2 — Preliminary overlap analysis

**Runner:**

```text
Codes/runners/run_topology.py
```

**Core module:**

```text
Codes/core/topology.py
```

**Input:**

```text
Results/Normalized_text_columns/BDR_CCDC_TNE_v3_textnorm.shp
```

**Output:**

```text
Results/Topologia_revisado/BDR_CCDC_TNE_v3_textnorm_tplgy.shp
```

This stage performs a preliminary self-overlap analysis and adds:

```text
Tplgy_error
```

The value is `True` when a polygon overlaps another polygon by more than the configured minimum overlap area.

The default execution uses:

```text
min_overlap_area = 1.0
```

expressed in the units of the input CRS, normally square metres for the projected BDR layer.

This preliminary topology output is used as the input to the harmonization stage. However, the final `Validation_flag` is recalculated independently inside the harmonization pipeline using a more complete QGIS-like gaps-and-overlaps procedure.

### 2.3 Stage 3 — Harmonization and final export

**Runner:**

```text
Codes/runners/run_process_layer_BDR.py
```

**Pipeline:**

```text
Codes/pipelines/process_layer_BDR.py
```

**Input:**

```text
Results/Topologia_revisado/BDR_CCDC_TNE_v3_textnorm_tplgy.shp
```

**Outputs:**

```text
Results/Harmonizacion_datos/BDR_CCDC_TNE_v3_harmonized.gpkg
Results/Harmonizacion_datos/BDR_CCDC_TNE_v3_harmonized_report.xlsx
```

This stage:

- validates required input fields;
- standardizes temporal fields;
- creates harmonized identifiers;
- derives the change type;
- calculates polygon area;
- recalculates topology-based validation flags;
- assigns the administrative code;
- assigns the Sentinel-2 tile when the complete polygon lies within one unique tile;
- retains only the harmonized schema;
- normalizes all final text values;
- reprojects and exports the final layer to `EPSG:3763`;
- creates a field-mapping report.

### 2.4 Separation from BDR expanded

The BDR expanded layer is not processed by:

```text
Codes/runners/run_process_layer_BDR.py
```

It has its own independent runner:

```text
Codes/runners/run_process_layer_BDR_expanded.py
```

The BDR expanded runner uses:

```text
Results/Topologia_revisado/Cleaned_1.shp
```

and creates:

```text
Results/Harmonizacion_datos/BDR_expanded.gpkg
Results/Harmonizacion_datos/BDR_expanded.xlsx
```

Both BDR and BDR expanded use the shared harmonization function `harmonize_bdr_layer()`, but they are executed separately and receive different source names and unique identifier prefixes.

## 3. Required input and support data

### 3.1 Main BDR input

The standard input layer is:

```text
Data/BDR_CCDC_TNE_v3.shp
```

The input layer must:

- exist at the expected path;
- contain a defined CRS;
- use a projected CRS suitable for area calculations;
- contain the required class and buffer fields.

### 3.2 Administrative reference layer

The harmonization pipeline requires:

```text
NUTS/areas_administrativas.shp
```

Required attribute:

```text
dtmnfr
```

This layer is used to derive `Pi_dicofre`.

### 3.3 Sentinel-2 tile reference layer

The harmonization pipeline also requires:

```text
S2_tiles/sentinel2_tiles_PT_terra_tm06.shp
```

This layer is used to derive `S2_tile`.

The pipeline searches for `NUTS` and `S2_tiles` in either of these locations:

```text
<parent directory of BDR_DGT_300>/NUTS/
<parent directory of BDR_DGT_300>/S2_tiles/
```

or, as a fallback:

```text
BDR_DGT_300/NUTS/
BDR_DGT_300/S2_tiles/
```

## 4. Input validation and required fields

The harmonization pipeline accepts alternative capitalization and spelling for several input fields.

### 4.1 Required class fields

The pre-change class is detected from the first available field among:

```text
classe_0
clase_0
Classe_0
Clase_0
```

The post-change class is detected from:

```text
classe_1
clase_1
Classe_1
Clase_1
```

Internally, these fields are standardized as:

```text
classe_0
classe_1
```

and exported as:

```text
Classe_0
Classe_1
```

### 4.2 Required buffer identifier

The buffer identifier is detected from:

```text
buffer_ID
buffer_id
Buffer_ID
Buffer_id
```

It is standardized internally as `buffer_ID` and exported as `Buffer_id`.

Values are cleaned as follows:

- NULL-like values remain NULL;
- empty strings become NULL;
- text values such as `NULL`, `NAN`, `NONE`, or `NAT` become NULL;
- numeric-looking strings ending in `.0` are cleaned, for example `123.0` becomes `123`.

### 4.3 Temporal input fields

The start date is detected from:

```text
data_0
Data_0
DATA_0
Data0
DATA0
```

The end date is detected from:

```text
data_1
Data_1
DATA_1
Data1
DATA1
```

If either field is absent, the corresponding harmonized field is created with NULL values. The current implementation does not stop solely because `Data0` or `Data1` is absent.

## 5. Temporal standardization

The pipeline converts temporal values to:

```text
YYYY-MM-DD
```

Supported inputs include:

- Python `date` values;
- Python `datetime` values;
- Pandas `Timestamp` values;
- strings such as `2020-09-11`;
- datetime strings such as `2020-09-11 00:00:00`;
- integer or string representations such as `20200911`.

Invalid or unrecognized date values become NULL.

The pipeline prints a date-conversion check showing:

- number of non-NULL input values;
- number of non-NULL standardized values;
- number of values lost during conversion;
- examples of values that could not be converted.

### 5.1 Global evaluation period

In the current implementation, the evaluation period is assigned as a fixed project-wide interval to every record:

```text
Temp_eval_start = 2018-09-01
Temp_eval_end   = 2021-09-30
```

These fields are not currently calculated as the maximum or minimum between `Data0`, `Data1`, and the global evaluation limits. They are constant values in the active pipeline.

## 6. Topological validation

Two related but different topology procedures are used.

### 6.1 Preliminary overlap flag

The standalone topology stage creates:

```text
Tplgy_error
```

This field only identifies overlaps between polygons and is generated by:

```text
Codes/core/topology.py
```

### 6.2 Final harmonized validation flag

During harmonization, topology is recalculated using polygonized boundary faces and coverage counts.

The procedure:

1. validates or repairs geometries;
2. combines polygon boundaries;
3. polygonizes the combined boundaries into faces;
4. removes the largest exterior face;
5. counts how many input polygons cover each internal face;
6. identifies:
   - overlaps where a face is covered by more than one polygon;
   - gaps where an internal face is covered by no polygon;
7. flags the features involved in overlaps or touching internal gaps.

The final field is:

```text
Validation_flag
```

Before final text normalization, the pipeline assigns:

```text
Topology error
No topology error
```

After final normalization, the values stored in the output are:

```text
topology error
no topology error
```

The topology analysis flags possible inconsistencies but does not modify the polygon geometries.

## 7. Creation of harmonized attributes

The final BDR output contains the following harmonized fields:

```text
Src
Id
Uid
Data0
Data1
Temp_eval_start
Temp_eval_end
Chg_type
Area_ha
Validation_flag
Pi_dicofre
S2_tile
Classe_0
Classe_1
Buffer_id
geometry
```

When `keep_only_harmonized=True`, fields outside this schema are removed from the final GeoPackage.

### 7.1 Src

- **Type:** string
- **Value for BDR:** `bdr`
- **Purpose:** Identifies the source dataset in the common harmonized framework.

For BDR expanded, the separate runner assigns:

```text
bdr_expanded
```

### 7.2 Id

- **Type:** integer
- **Description:** Sequential identifier generated from 1 to the total number of features.
- **Purpose:** Supports processing and spatial joins within the harmonization workflow.

### 7.3 Uid

- **Type:** string
- **Format for BDR:** `bdr_XXXXXXX`
- **Purpose:** Provides a source-specific unique identifier.

The numeric suffix is zero-padded to seven positions.

For BDR expanded, the independent runner produces:

```text
bdr_expanded_XXXXXXX
```

### 7.4 Data0

- **Type:** date string (`YYYY-MM-DD`) or NULL
- **Description:** Standardized start date of the change interval.
- **Source:** First available supported start-date field.
- **Purpose:** Preserves the original start of the potential change interval.

### 7.5 Data1

- **Type:** date string (`YYYY-MM-DD`) or NULL
- **Description:** Standardized end date of the change interval.
- **Source:** First available supported end-date field.
- **Purpose:** Preserves the original end of the potential change interval.

### 7.6 Temp_eval_start

- **Type:** date string (`YYYY-MM-DD`)
- **Current value:** `2018-09-01`
- **Description:** Fixed start of the project-wide evaluation period.

### 7.7 Temp_eval_end

- **Type:** date string (`YYYY-MM-DD`)
- **Current value:** `2021-09-30`
- **Description:** Fixed end of the project-wide evaluation period.

### 7.8 Chg_type

- **Type:** string or NULL
- **Description:** Disturbance type assigned when the feature represents a change.
- **Source:** `tipo_1`, combined with either `altera` or `Change`.

When `altera` exists:

- values containing `sem alteracao` are treated as no change;
- all other records receive the corresponding `tipo_1`.

When `altera` is absent and `Change` exists:

- values containing `change` are considered changes;
- values containing `no change`, `not aplicable`, or `not applicable` are excluded.

The final values are normalized to lowercase and accents are removed.

### 7.9 Area_ha

- **Type:** float
- **Description:** Polygon area expressed in hectares.
- **Derivation:**

```text
Area_ha = geometry area / 10,000
```

The input must use an appropriate projected CRS before this calculation.

### 7.10 Validation_flag

- **Type:** string
- **Final values:**
  - `topology error`
  - `no topology error`
- **Description:** Indicates whether a polygon participates in an overlap or touches an internal gap detected by the final QGIS-like topology procedure.

### 7.11 Pi_dicofre

- **Type:** string or NULL
- **Description:** Administrative code derived from `dtmnfr`.
- **Method:** Spatial join using the centroid of each BDR polygon.

The join first uses the `within` predicate. If no match is obtained, it tries `intersects`. When more than one candidate is present, the first available match is retained.

### 7.12 S2_tile

- **Type:** string or NULL
- **Description:** Sentinel-2 tile assigned to the feature.
- **Method:** The complete BDR polygon must be spatially `within` one unique Sentinel-2 tile.

Assignment rules:

- one unique full-geometry match → tile code is assigned;
- no match → NULL;
- more than one match → NULL.

The pipeline attempts to identify the tile code from common field names such as:

```text
Name
Tile
Tile_id
Tile_name
MGRS_TILE
S2_TILE
Id
```

The final value is normalized to lowercase. For example:

```text
T29TNE → t29tne
```

### 7.13 Classe_0

- **Type:** string or NULL
- **Description:** BDR pre-change or level-0 class.
- **Source:** Standardized from `classe_0` or its accepted variants.
- **Final normalization:** lowercase, no accents or diacritics.

Examples:

```text
Eucalipto → eucalipto
Pinheiro bravo → pinheiro bravo
```

### 7.14 Classe_1

- **Type:** string or NULL
- **Description:** BDR post-change or level-1 class.
- **Source:** Standardized from `classe_1` or its accepted variants.
- **Final normalization:** lowercase, no accents or diacritics.

### 7.15 Buffer_id

- **Type:** string or NULL
- **Description:** Cleaned identifier of the original BDR buffer.
- **Purpose:** Preserves traceability to the original BDR sampling unit.

## 8. Final text normalization

The final harmonization pipeline applies text normalization after creating and renaming the harmonized fields.

The corrected implementation recognizes:

```text
object
string[python]
string[pyarrow]
```

For all recognized text columns, it:

- applies normalization value by value;
- converts text to lowercase;
- removes accents and diacritics;
- strips surrounding spaces;
- preserves NULL values.

The following date fields are explicitly excluded:

```text
Data0
Data1
Temp_eval_start
Temp_eval_end
```

The geometry column is also excluded.

This correction ensures that values such as:

```text
T29TNE
Eucalipto
Pinheiro bravo
Superfície sem vegetação
```

are exported as:

```text
t29tne
eucalipto
pinheiro bravo
superficie sem vegetacao
```

The final field names remain defined by the harmonized schema, for example `S2_tile`, `Classe_0`, and `Classe_1`. The normalization applies to their values, not to the capitalization of the field names.

Relevant code:

```text
Codes/pipelines/process_layer_BDR.py
Codes/utils/normalize_string.py
```

## 9. CRS and final export

The pipeline requires the input BDR layer to have a defined CRS.

Administrative boundaries and Sentinel-2 tiles are reprojected to the BDR input CRS before spatial joins when necessary.

After harmonization, the final BDR layer is reprojected and written using:

```text
Codes/core/reproject_layer.py
```

Final CRS:

```text
EPSG:3763
```

Final GeoPackage:

```text
Results/Harmonizacion_datos/BDR_CCDC_TNE_v3_harmonized.gpkg
```

## 10. Field-mapping report

The pipeline creates:

```text
Results/Harmonizacion_datos/BDR_CCDC_TNE_v3_harmonized_report.xlsx
```

The report documents the relationship between input and output fields using:

```text
original_name
final_name
status
```

Possible status values include:

```text
kept_and_renamed
dropped
added
```

This report is a schema-traceability report. It does not currently provide NULL percentages or exploratory value summaries.

## 12. Status

The standard BDR reference layer has a defined and reproducible three-stage processing sequence:

1. text normalization;
2. preliminary overlap analysis;
3. harmonization and final export.

The final layer is prepared for integration and comparative analysis with the other harmonized reference datasets. BDR expanded remains a separate product with its own runner and documentation.
