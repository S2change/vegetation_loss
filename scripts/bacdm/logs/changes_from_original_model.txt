Revise checkpoints:

Yes, strongly recommended — especially for HPC runs where you can't monitor closely.

The main reasons in your specific case:

Your loss_least variable (line 134) is initialized but never used — you're saving every epoch's checkpoint with no way to select the best one. Validation loss gives you that signal.
You're using high class weights (rare classes) which makes overfitting more likely and harder to detect from training loss alone.
On HPC you'll want automatic best-checkpoint saving rather than manually inspecting dozens of .pth files.
Practical recommendation: a 90/10 or 85/15 train/val split is typical for segmentation. The tradeoff is that with very few samples of rare classes (your classes 1–4 sound sparse), a random split risks putting all rare-class examples in one partition — so a stratified split at the chip level (by dominant class or by geographic region) is safer than pure random.

For implementation, the cleanest approach is:

Split the chip file list into train/val at the dataset level (in MyData or via a pre-generated text file listing train vs val chips)
After each epoch, run inference on the val set with torch.no_grad(), compute val loss and per-class IoU
Save checkpoint only when val loss improves (replacing your unused loss_least logic)
